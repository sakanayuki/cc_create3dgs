# 01. 要件と決定事項

## 1.1 プロダクト定義

スマートフォンのブラウザで、手持ちの写真1枚から3D Gaussian Splatting を生成し、その場で回して見て、ファイルとして書き出せるWebアプリ。

一言で言えば **「写真を立体にして持ち帰る」** ツール。生成はすべて端末内で行われ、写真がネットワークに出ることはない。

## 1.2 確定した決定事項

ヒアリングで確定した内容。以降の全設計はこれを前提とする。

| # | 項目 | 決定 | 影響範囲 |
|---|---|---|---|
| D1 | 生成の実行場所 | **完全オンデバイス**（ブラウザ内100%） | 使用モデルの規模上限を決定づける。→ §1.3 |
| D2 | 出力の立体性 | **半球カバー**（±60°程度、裏側は補完） | 背面シェル生成が必須機能に。→ [03](./03-pipeline.md) |

| D6 | ライセンス方針 | **未定・両方に備える**（差し替え可能な構造、既定は商用可） | モデルレジストリ機構が必要 |

| D10 | CIの責務 | ビルド+Pagesデプロイ / モデル量子化(キャッシュ付) / 自動テスト / 性能バジェット監視 の**4つすべて** | → [07](./07-cicd.md) |

| D14 | 設計書形式 | `docs/` に Markdown + 閲覧用HTMLページ | 本文書群 |

### D4 と D13 の関係について

「最優先KPIは生成速度」（D4）と「10秒以内で良いから高品質」（D13）は一見矛盾するため、次のように解釈を確定する。

> **10秒は超えてはならない上限（ハードバジェット）であり、その予算内では品質に投資する。**
> 速度が最優先KPIであるとは、「品質のために10秒を12秒に延ばす」という判断を禁じる、という意味である。

したがって設計上のルールは次の2つになる。

1. どの品質向上策も、時間予算表（[03](./03-pipeline.md#38-時間予算)）に枠を確保できる場合にのみ採用する。
2. 予算を超えそうな処理は、削るのではなく **プレビュー後のバックグラウンド処理に回す**。ユーザーが待つ時間と、処理が終わる時間を分離する。

## 1.3 なぜ完全オンデバイスが TripoSplat を排除するのか

D1（完全オンデバイス）は、使えるモデルの規模を厳しく制限する。TripoSplat の公式重みを実測した結果は次の通り。

| ファイル | サイズ (fp16) |
|---|---|
| `clip_vision/dino_v3_vit_h.safetensors` | 1,681 MB |
| `diffusion_models/triposplat_fp16.safetensors` | 741 MB |
| `vae/triposplat_vae_encoder_fp16.safetensors` | 682 MB |
| `vae/triposplat_vae_decoder_fp16.safetensors` | 576 MB |
| `background_removal/birefnet.safetensors` | 445 MB |
| `vae/flux2-vae.safetensors` | 336 MB |
| **合計** | **約 4,461 MB** |

int4 まで量子化しても1GBを超え、さらに20ステップの拡散サンプリングを要する。
iOS Safari はタブのメモリ使用量が概ね1〜1.5GBを超えると強制終了するため、モバイルブラウザでの実行は成立しない。
また GitHub Pages は静的ホスティングのみでサーバ推論を置けない（D7・D8）。

**結論**: オンデバイスで実現可能なのは、単眼深度推定を軸とした幾何ベースの再構成である。
これは 360° の完全なオブジェクトを作る手法ではないが、D2（半球カバー）の範囲であれば十分な品質に到達できる。

## 1.4 性能SLO

基準端末: **iPhone 14 / Google Pixel 7 相当**（2022年発売の中位機）。

| 指標 | 目標 | 上限（超えたらCI失敗またはリリース判定NG） |
|---|---|---|
| 画像選択 → 操作可能なプレビュー表示 | 4.6 秒 | 6.0 秒 |
| 画像選択 → 全処理完了（微調整・量子化含む） | 7.7 秒 | **10.0 秒** |
| 初回訪問時のモデルダウンロード（人物モード） | 25.6 MB | 30 MB |
| 初回訪問時のモデルダウンロード（物体モード追加分） | 44 MB | 50 MB |
| 閲覧時のフレームレート | 60 fps | 30 fps を下回らない |
| `.pgs` 書き出しサイズ | 350 KB | 500 KB |
| JSバンドル (gzip) | 280 KB | 400 KB |

上記のうち**時間に関する指標はCIで測定できない**（GitHubランナーにGPUがなく、WebGPUはソフトウェアエミュレーションになるため）。
CIが強制するのはサイズと品質の静的指標のみで、時間は実機での手動計測を記録する。詳細は [07](./07-cicd.md#75-性能バジェットの現実的な線引き)。

## 1.5 D7「リポジトリ同梱」の正確な意味

「同梱」には2つの解釈があり、ヒアリングでの回答（同梱 + CIで量子化しキャッシュ）は次の組み合わせを指す。

- **git リポジトリには量子化済みバイナリをコミットしない。** モデル更新のたびに履歴が肥大化し、Pages の 1GB 制限を圧迫するため。
- **CI が量子化した成果物を、ビルド成果物として `dist/models/` に配置し Pages にデプロイする。**

結果として、ブラウザから見れば `https://<user>.github.io/<repo>/models/*.onnx` という**同一オリジン**でモデルが配信される。
CORS 設定が不要で、外部サービス（HuggingFace CDN 等）の可用性にも依存しない。リポジトリは軽いまま保たれる。

## 1.6 スコープ外（今回は作らないもの）

明示的に作らないものを列挙する。将来やるかもしれないが、本設計の対象外。

- 360°の完全なオブジェクト生成（TripoSplat 相当）。オンデバイスでは実現不可能。
- 複数枚の写真からの再構成（Structure from Motion / 一般的な3DGS学習）。
- サーバへのアップロード、URL共有、生成物のクラウド保存。
- 動画・GIFの書き出し。
- カメラのライブプレビュー（`getUserMedia`）。ファイル選択ダイアログからOS標準のカメラを呼べるため、優先度が低い。
- PWA・オフライン動作・Service Worker。
- 多言語対応。
- 風景・室内シーン全体の再構成（被写体が画面全体を占めるため背景除去が機能せず、必要ガウシアン数も跳ね上がる）。
- WebGL2 フォールバック（描画・推論とも）。ただし推論のみ WASM フォールバックを持つ。→ [08](./08-risks.md#r1)

## 1.7 参考文献の評価

依頼時にご提示いただいた2文献について、調査した結果を記録する。**両者の役割は当初の想定と入れ替わっていた。**

### KISS-GS — 本設計の主要な下敷き

[KISS-GS: 3D Gaussian Splatting Compression Kept Simple](https://fraunhoferhhi.github.io/KISS-GS/) (Fraunhofer HHI, ECCV 2026, arXiv 2608.26948)

単一画像からの生成手法ではなく、**学習済み3DGSシーンの圧縮パイプライン**である。次の3段を独立に適用する。

1. **Compaction**: プルーニング手法の組み合わせでプリミティブ数を 15.7× 削減
2. **Encoding (SOG-XT)**: 属性を2D画像グリッドに並べ替え、8bit画像コーデックで圧縮して 6.6× 削減。自己組織化2Dコードブックと PRAS (Parallel Representative Assignment Smoothing) を導入
3. **符号化を織り込んだ微調整**: 圧縮をループに含めた最適化で追加 2.2× 削減

総合で vanilla 3DGS 比 85〜319×。Garden シーンの 256k スプラットが 3.94MB。デコードは NumPy 実装で 108ms、GPU不要。WebGL でのブラウザ再生実績あり。

**本設計への採り入れ方**: 4階層の軽量化のうち、L2（属性の2D画像化）と L3（量子化を織り込んだ微調整）は KISS-GS の思想をそのまま踏襲する。
ただし後述の通り、**単一画像ケースでは最も重い工程である「並べ替え」が不要になる**という構造的な優位がある。→ [04](./04-compression.md#43-l2-属性の2d画像化)

### TripoSplat — 到達点の参照のみ

[TripoSplat](https://github.com/VAST-AI-Research/TripoSplat) (VAST-AI Research, MIT ライセンス、重みも MIT)

単一の2D画像から高品質な3DGSを生成する。DINOv3 ViT-H による画像エンコード → triplane 生成 → ガウシアンデコード。最大 262,144 ガウシアン、可変個数に対応。出力は `.ply` / `.splat`。

**本設計への採り入れ方**: §1.3 の通り規模が大きすぎるため、モデルとしては採用しない。
ただし「ガウシアン数を可変にして品質と描画コストをトレードオフさせる」という設計思想と、上限 262,144 という数値は、本設計のガウシアン予算（[04](./04-compression.md#42-l1-個数の削減)）の参考にしている。

## 1.8 用語

| 用語 | 意味 |
|---|---|
| 3DGS | 3D Gaussian Splatting。シーンを多数の3次元ガウシアン（楕円体）の集合で表現し、それを画面に投影(splat)して描画する手法 |
| ガウシアン / スプラット | 3DGSの構成単位。位置・スケール・回転・不透明度・色を持つ |
| SH | Spherical Harmonics（球面調和関数）。3DGSで視点依存の色を表現するのに使われる。次数0はDC成分＝視点非依存の単色 |
| サーフェル (surfel) | 厚みを持たない平たいガウシアン。法線方向のスケールがほぼ0のもの |
| 前面シェル | 入力画像から直接見えている面を表すガウシアン群 |
| 背面シェル | 見えていない裏側を推定して生成するガウシアン群。半球カバー(D2)の実現に必須 |
| スカート (skirt) | 深度の不連続な縁に沿って生成する、視点移動時に穴が開くのを防ぐガウシアン群 |
| 遮蔽解消 (disocclusion) | 視点を動かした結果、それまで隠れていた領域が露出すること |
| QAT | Quantization-Aware Training。量子化誤差を織り込んだ最適化 |
| STE | Straight-Through Estimator。量子化のような微分不可能な演算を勾配計算で素通しさせる手法 |
| PLAS | Parallel Linear Assignment Sorting。3DGS属性を2Dグリッドに空間的コヒーレンスを保って並べ替えるアルゴリズム |
| SLO | Service Level Objective。守るべき性能目標 |
