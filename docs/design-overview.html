前提の訂正

設計に入る前に、いただいた前提のうち2点が事実と異なっていました。設計全体がこの2点の上に立っているため、最初に置きます。

訂正 1 — 参考文献の役割が入れ替わっています

KISS-GS（Fraunhofer HHI, ECCV 2026, arXiv 2608.26948）は、単一画像からの生成手法ではなく 3DGS の圧縮パイプラインです。属性を2D画像に並べ替えて画像コーデックに載せる SOG-XT により、vanilla 3DGS 比 85〜319× を達成しています。

TripoSplat（VAST-AI, MIT）のほうが 単一画像 → 3DGS の生成手法です。本設計では、軽量化の下敷きに KISS-GS を、品質の到達点の参照に TripoSplat を使います。

訂正 2 — TripoSplat はスマホブラウザでは動きません

HuggingFace の公式重みを実測したところ、fp16 で 合計 4,461 MB ありました。内訳は DINOv3 ViT-H が 1,681 MB、拡散モデル 741 MB、VAE エンコーダ 682 MB、VAE デコーダ 576 MB、背景除去 445 MB、flux2-vae 336 MB。さらに20ステップの拡散サンプリングが要ります。

int4 まで量子化しても1GBを超え、iOS Safari がタブを落とすメモリ帯に入ります。GitHub Pages は静的配信のみでサーバ推論も置けません。オンデバイス完結（決定 D1）を守るなら、単眼深度推定を軸にした幾何ベースの再構成しか選択肢がありません。

訂正 3 — Three.js の splat レンダラはまだリリースされていません

ご選択いただいた「Three.js ネイティブ WebGPU splat レンダラ (r186+)」は dev ブランチにマージ済みですが、npm 最新の three@0.185.1 には splat モジュールが一切含まれていません（jsDelivr のファイル一覧で確認）。r186 のリリースを待つ形になります。

そのため描画層に薄い抽象インタフェースを1枚挟み、まず自前 WGSL 実装で進め、r186 が出たら差し替える設計にしています。

⑨量子化・符号化 — 属性を4枚の画像プレーンにパックし、PNG / WebP で符号化0.55 s
半球カバー（D2）をどう成立させるか

前面シェルだけでは、横に回した瞬間に紙のような板に見えます。そこでシルエットの内部距離変換 D(u,v) から 楕円断面の厚み t = T·√(1−(1−D/Dmax)²) を与え、閉じた殻を作ります。境界で厚み0、中心で最大になるため、円柱状にした場合の角張った縁が出ません。

背面の色は前面色の水平反転＋厚みに応じた減光。人物の後頭部や物体の裏面として違和感が少なく、コストは 0.02 秒です。インペイントモデルを足せば最良ですが +2秒 +50MB で予算を壊すため採りません。背面は正面から見えないので、2×2画素を1ガウシアンにまとめた 1/4 密度で足ります。

04

軽量化の4階層

「量子化などの軽量化技術を深く」というご要望への回答。独立した4階層が乗算的に効きます。KISS-GS が報告する 85〜319× と同オーダーに達しますが、その理由は技術力ではなく、単一画像由来という構造的な有利さです。

L0 — 表現の削減 画質損失ゼロ

SH 1〜3次（180 B）を捨てて次数0に固定。単一画像からは視点依存の色を観測できないので、持たせても無根拠な外挿にしかなりません。標準PLYの未使用法線フィールド（12 B、常に0）も捨て、全ガウシアンをサーフェル化して回転クォータニオンを法線に、スケールを3軸から2軸に。248 B → 48 B。

L1 — 個数の削減

被写体単体を対象とする要件から、背景除去だけで画面の60%が消えます（2.5×）。さらに四分木で分散の小さいセルを統合し40%削減。重要度プルーニングは既定でほぼ行いません — 個別に間引くと画像平面に穴が開き、L3 の圧縮効率を落として差し引きゼロになるためです。

L2 — 数値精度の削減

属性ごとのビット割当。基準は「その属性の誤差が最終画像に何ピクセル分の誤差として現れるか」で、全属性を1画面ピクセル以下に揃えます。ある属性だけ精度を上げても他がボトルネックになり、サイズだけが増えるためです。48 B → 11.6 B。

L3 — 画像化と符号化

KISS-GS の SOG-XT と同じ発想で、属性を2D画像に並べて PNG / WebP に載せます。ただし本設計では並べ替え工程が丸ごと不要（下の囲み）。さらに位置・法線・スケール・厚み・背面色・スカートは保存すらしません。

核心 — なぜ本設計では「並べ替え」が要らないのか

一般の3DGSでは、ガウシアンは3D空間に散らばった順不同の集合です。これを「隣接ピクセルの値が似る」ように2Dグリッドへ並べ替えるのが、画像コーデックを効かせるための前提であり、圧縮全体で最も重い工程になります。KISS-GS / SOG は PLAS（Parallel Linear Assignment Sorting）を使い、数十万プリミティブに GPU で数秒〜数十秒かけます。

深度マップから生成されたガウシアンは、元から画像のピクセル格子に1対1で乗っています。ピクセル (u,v) から作ったガウシアンをそのまま (u,v) に置けばよく、その並び順の空間的コヒーレンスは入力写真そのものが持つコヒーレンスです。並べ替えアルゴリズムが探しにいく理想解に、定義上そのまま一致しています。

単一画像・深度ベースであることから来る構造的な優位で、決定 D4（生成速度が最優先）に直接効きます。数秒の工程がゼロになります。

保存しないもの

画像平面に乗ったことで、多くの属性が「決定的な導出物」になります。

属性保存復元方法
位置不要ピクセル座標 + 深度 + カメラ内部パラメータから逆投影。3成分12Bが深度1成分に縮む
法線不要深度マップの局所平面フィットから導出
スケール（基準）不要s = k·z/focalPx で深度から決まる
厚み（背面）不要α からの距離変換で決定的に求まる。パラメータ T のみ保存
背面の色不要前面色の水平反転＋減光
スカート全体不要深度エッジ検出は frontDepth と alpha の決定的な関数
深度・色・不透明度・スケール補正保存4枚の画像プレーンとして PNG / WebP に
背面シェルとスカートを保存しなくてよい、もう一つの理由

微調整の損失は「入力画像のカメラ位置から描画した結果」と入力画像の差で定義されます。そのカメラから見て、背面シェルとスカートは前面シェルに完全に遮蔽されています。したがって勾配が届かず、最適化されません。ならば保存する必要もない。

これは偶然ではなく、「単一視点の情報しか無いのだから、見えないものは最適化できないし、決定的な規則で作るしかない」という一貫性の表れです。

深度プレーンの扱い — 非自明だが効く一手

12bit に落として、上位8bit と 下位4bit に分離する

16bit のまま保存してはいけません。深度の実効的な有効精度は12bit程度なので、16bit で持つと下位4bitは実質ノイズになり、PNG の予測フィルタ後の残差がランダム化して圧縮率が壊滅します。精度が要らないビットを持つことは、単に無駄なのではなく有害です。

上位/下位に分離する理由。PNG のフィルタはバイト単位で動きます。16bit グレースケールを1枚で持つと、滑らかな上位バイトと不規則な下位バイトが交互に並び、どちらの予測も当たりません。分離すれば上位プレーンは非常に滑らかで高圧縮、下位プレーンは4bit分のエントロピーしか持ちません。この2点だけで、深度プレーンのサイズが素朴な実装の約 1/3 になります。

07

CI / Pages

D10 の4責務すべてを GitHub Actions だけで実装します。外部サービスには依存しません。

1deploy.yml — モデル取得（キャッシュ）→ 量子化 → ビルド → バジェット判定 → Pages デプロイ。main への push で起動約 3 分
2quantize.yml — 量子化設定が変わったPRで、base側とhead側の両方を量子化して精度差分をPRにコメント約 12 分
3test.yml — 単体・結合に加え、Playwright + headless Chrome（SwiftShader）でサンプル画像から実際に生成して検証約 4 分
4budget.yml — バンドル・モデル・出力サイズ・再構成品質のバジェット判定。warn はコメント、fail はCIを落とす約 3 分
モデル量子化をCIでやることの、本当の価値

キャッシュキーを「レジストリ＋量子化スクリプト＋較正データ」のハッシュにするので、通常のデプロイでは再量子化は走らず数十秒で終わります。フル実行されるのは量子化設定を変えたPRだけです。

価値の中心は excludeOpTypes — どの演算を量子化から除外すると精度が保てるかは、事前には分からず試して測るしかありません。深度推定では LayerNorm と Softmax の精度が支配的で、ここを量子化すると相対絶対誤差が跳ね上がります。CIに載っていれば「除外リストを1行変えたPR」に対して自動で精度差分が出るので、数値を見ながら詰められます。手元の手作業では、この探索は現実的に回りません。

較正は人物6枚・物体6枚の計12枚。深度は AbsRel < 2.0% と δ<1.05 精度 > 97% の両方を見ます。AbsRel だけだと、顔の中央だけがへこむような局所的な破綻を見逃すためです。

正直に線を引きます — 時間はCIで測れません

GitHubランナーにはGPUがなく、Chrome は SwiftShader（ソフトウェア実装）で動きます。実機の20〜50倍遅いので、そこで測った「生成時間」は実機の性能について何も語りません。

したがって CIが強制するのはサイズと品質の静的指標のみです。バンドル・モデル・出力サイズ、ガウシアン数、入力視点でのSSIM、±40°回転時の穴の割合、量子化前後の精度差。時間は実機で ?bench=1 モードを使って手動計測し、docs/measurements.md に端末名と日付つきで記録します。

「CIが通ったから速い」と誤認するより、測れないことを明示しておくほうが安全だと判断しました。

リスクとPoC

本実装に入る前に、合計4〜6日のPoCで前提を検証します。順序には理由があります。

IDリスク影響確率対策
R1ONNX Runtime Web の WebGPU EP が iOS Safari で動かない致命的中3段の縮退（q4f16 → fp16 → WASM uint8）。PoC-1 で最優先検証
R2q4f16 量子化で深度が破綻する大中LayerNorm/Softmax を除外、DPTヘッドは量子化しない、最終手段は fp16
R3背面シェルの見た目が許容できない大中減光を強める → 単色化 → 厚み0（前面のみ）。カメラ回転制限とビネットが最大の保険
R4Three.js r186 が長期間リリースされない中中レンダラ抽象レイヤ。自前WGSL実装を先に作る
R5深度プレーンの圧縮率が想定に届かない中中10bitに落とす／平滑化してから量子化／色プレーンのqで融通
R6iOS のメモリ上限でタブが落ちる大低ピーク約630MBの見積もり。セグメンテーションと深度のセッションを同時に持たない
R710秒 SLO に収まらない中中削るのではなく、優先度2以降をプレビュー後に回す。量子化は書き出し時まで遅延
R1 だけは性質が違います

WebGPU 自体は iOS 26 / Safari で使えますが、ONNX Runtime Web の WebGPU EP が iOS 上で安定動作するかは別問題です。ORT の検証は Chrome / Desktop 中心で、Safari 特有の実装差で失敗しうる。さらに q4f16 は MatMulNBits という比較的新しい演算子を使い、Safari で動く保証がありません。

そこで他の何よりも先に、これだけを検証する1ファイルのHTMLを作り、Pages にデプロイして実機の iPhone と Android で開きます。3つの量子化構成の成否・所要時間・出力の妥当性を画面に出すだけのもので、1〜2日。この結果が出るまで本実装に入りません。

3段すべて失敗した場合、D1（完全オンデバイス）を諦めて外部APIを使うしかなく、それは要件の変更なのでご相談することになります。
