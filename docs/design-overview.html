v2 レビュー要旨

v1 は速度を軸に書かれていた。v2 は「品質」を軸に第三者レビューを行い、品質に直結する問題だけを直した。変えたのは4つ、変えなかったのは軸そのものである。

直した 1 — 微調整の見積もりが非現実的で、効果も的外れだった

v1 は「微分可能ラスタライズ 1反復 6ms × 400 = 2.4秒」と見積もっていたが、forward+backward はデスクトップGPUの gsplat でも 10〜20ms/反復。スマホでは 16〜32秒になり、10秒SLOを単独で壊す。しかも教師は入力視点1枚で、深度由来の3DGSは入力視点からは元からほぼ完全に再現できる。斜めから見た品質には一切効かない。

→ QAT を廃止し、40〜60反復・256² の「継ぎ目補正」（0.6秒）に縮小。浮いた約2秒を下の2つに回した。

直した 2 — 遮蔽部の補完が「色の引き伸ばし」で、斜めからの破綻が最も目立つ

視点を振ると深度エッジの奥側に隠れていた領域が露出する。v1 はそこに奥側の色を伸ばして置いていた——2.5D 表現の典型的な「縞」になる。

→ MI-GAN（Picsart, ICCV 2023, MIT、モバイル向け設計、uint8 約8MB）で遮蔽領域をインペイントし、スカートの色を補完テクスチャからサンプルする。+0.9秒。

直した 3 — 深度の「シフト不定性」が形を歪めていた

Depth Anything V2 の出力は affine-invariant な逆深度。未知のシフト項 b は被写体の膨らみ・平坦さ、つまり形そのものを歪める。v1 の較正は尺度 a しか実質的に決めておらず、b は勘だった。

→ Depth Anything 3 Small（Apache-2.0、ONNX 104.7MB≒V2と同規模）を第一候補に。深度を直接予測するためシフト自由度が無く、焦点距離も推定するので「画角55°を仮定」が不要になる。V2 経路にはシルエット法線の事前分布による b の推定を追加。両者は PoC で実機比較して確定。

直した 4 — 512² は写真の解像度に対して低かった

色プレーンは写真そのもので、ここが品質の天井になる。→ 1024² を既定に。深度タイルパスの実効解像度（1036²）と揃う。ガウシアン数・出力サイズは約4倍、描画は背面カリング前提で 60fps ぎりぎり（R12）。

その他の修正

人物の背面色を「顔の鏡像」から縁色の無地陰影に／深度エッジの飛び画素をジョイントバイラテラルで締め、境界画素の深度を内側から引く／適応サンプリングの .pgs 格納を「読込時の決定的再計算」として仕様化／Mip-Splatting 流のアンチエイリアスを追加／快適視点範囲を ±45°、ハード上限を ±60° に分離。

変えなかったこと

完全オンデバイス（D1）、半球カバー（D2）、WebGPU 必須（D5）、同一オリジン配信（D7）、SH次数0・サーフェル化による表現の削減、そして「属性を画像として保存し、並べ替えは構造的に不要」という軽量化の論理。この骨格は v1 のまま正しい。

前提と決定

2つの参考文献の位置づけと、なぜ TripoSplat がオンデバイスでは選べないか。そして確定した18の決定。

参考文献の位置づけ

TripoSplat（VAST-AI, MIT）は単一画像→3DGS の生成手法。HuggingFace の公式重みを実測すると fp16 で合計 4,461 MB（DINOv3 ViT-H 1,681 / 拡散 741 / VAE enc 682 / VAE dec 576 / 背景除去 445 / flux2-vae 336）、さらに20ステップの拡散サンプリングが要る。int4 でも1GBを超え、iOS Safari のメモリ帯に入る。オンデバイス完結を守るなら、単眼深度推定を軸にした幾何ベースの再構成しか選択肢がない。品質の到達点としてのみ参照する。

KISS-GS（Fraunhofer HHI, ECCV 2026）は 3DGS の圧縮パイプライン。属性を2D画像化して画像コーデックに載せる SOG-XT（85〜319×）が、本設計の軽量化の下敷きになっている。

生成パイプライン

⑦の直後にプレビューを確定させ、⑧⑨を待たずに操作を始められる。品質投資の主軸は「入力視点の再現」から「見えない部分の妥当さ」へ移した。

⓪前処理 — EXIF回転補正、長辺1024pxへリサイズ、正方化0.10 s
①被写体抽出 — 人物は MODNet、物体は ISNet-general。高品質では人物にも ISNet（精密マット）1.50 s
②深度推定 — DA3-Small（第一候補）／V2-Small。全体パス＋被写体2×2タイルの高解像パスを最小二乗で整合2.40 s
③深度較正 v2 — 尺度 a（奥行き≈短辺0.65倍）。V2経路ではシルエット法線の事前分布でシフト b を推定。色とαをガイドにしたジョイントバイラテラルで深度エッジを締め、境界画素の深度は内側から引く0.35 s
④⑤⑥シェル構築 — 前面を逆投影、楕円断面の厚みで背面シェルを閉じ、深度エッジにスカート幾何を張る。人物の背面色は縁色の無地陰影、物体は鏡像0.35 s
⑦適応サンプリング — 四分木統合（標準 −30%、高品質は無効）。プレビュー確定0.15 s
⑧遮蔽部インペイント v2 — 深度エッジ奥側のバンド（4〜32px）を MI-GAN で補完。スカートの色をここからサンプル0.90 s
⑨継ぎ目補正 v2 — 256²・40〜60反復。色と不透明度のみ。統合セルの継ぎ目と重なり暗化を均す0.60 s
⑩量子化・符号化 — 6枚の画像プレーンにパック。書き出し時まで遅延可0.80 s
シフト b をシルエット法線から推定する（V2 経路）

滑らかな物体のシルエット上では、表面の法線は視線にほぼ直交する——「輪郭とは視線が表面に接する場所である」という定義から来る幾何的事実で、被写体の種類を問わない。そこで b* = argmin_b Σ_silhouette (n_b·v)² を黄金分割で解く。b は1次元、法線の再計算は GPU で 3ms、20回で 0.06 秒。b が小さすぎれば輪郭の法線が正面を向いたままになり、大きすぎれば輪郭より内側で寝る。その中間が形として最も自然になる。DA3 経路ではシフト自由度そのものが無いので不要——これが DA3 を第一候補にする実質的な理由でもある。

04

軽量化の4階層

独立した4階層が乗算的に効く。KISS-GS の 85〜319× と同オーダーに達するが、その理由は技術力ではなく、単一画像由来という構造的な有利さにある。1024² でもこの論理は変わらない——だから解像度を上げられた。

L0 — 表現の削減 画質損失ゼロ

SH 1〜3次（180 B）を捨てて次数0に固定。単一画像からは視点依存の色を観測できない。未使用法線（12 B）も捨て、サーフェル化で回転を法線に、スケールを2軸に。248 B → 48 B。

L1 — 個数の削減 v2 で弱めた

背景除去で画面の60%が消える（2.5×）。四分木統合は v1 の −40% から標準 −30%、高品質では無効に。1024² では1画素が十分小さく、統合の恩恵より継ぎ目のリスクが相対的に大きい。描画負荷は背面カリングと LOD で吸収する。

L2 — 数値精度の削減

属性ごとのビット割当。基準は「誤差が最終画像に何ピクセル分として現れるか」で、全属性を1画面ピクセル以下に揃える。1024² では 1px ≈ 1.0mm と要求が倍厳しくなるが、位置 11bit（0.49mm ≈ 0.5px）で足りる。48 B → 11.6 B。

L3 — 画像化と符号化 v2: 6プレーン

KISS-GS の SOG-XT と同じ発想で属性を2D画像として PNG / WebP に載せる。並べ替え工程が丸ごと不要（下の囲み）。位置・法線・スケール・厚み・スカート幾何・サンプリング分割は保存しない。v2 で背面色と補完テクスチャのプレーンが加わった——モデル出力は再現できないから保存する。

核心 — なぜ本設計では「並べ替え」が要らないのか

一般の3DGSでは、ガウシアンは3D空間に散らばった順不同の集合であり、「隣接ピクセルの値が似る」よう2Dグリッドへ並べ替えることが画像コーデックを効かせる前提になる。KISS-GS / SOG は PLAS（Parallel Linear Assignment Sorting）で数十万プリミティブに GPU で数秒〜数十秒かける。

深度マップから生成されたガウシアンは、元から画像のピクセル格子に1対1で乗っている。ピクセル (u,v) のガウシアンをそのまま (u,v) に置けばよく、その並び順のコヒーレンスは入力写真そのもののコヒーレンスである。並べ替えが探しにいく理想解に、定義上そのまま一致する。1024² に上げても、このコストはゼロのまま。

07

CI / Pages

4責務すべてを GitHub Actions だけで実装。外部サービスには依存しない。

1deploy.yml — モデル取得（キャッシュ）→ 量子化 → ビルド → バジェット判定 → Pages デプロイ約 3 分
2quantize.yml — 量子化設定が変わったPRで base/head 両方を量子化し精度差分をPRにコメント。v2 で DA3-S vs V2-S の比較（DA3-Large fp32 を評価専用の擬似正解に）と MI-GAN の PSNR を追加約 12 分
3test.yml — Playwright + headless Chrome（SwiftShader）でサンプル画像から生成し検証。v2 で「±45° の縞指標」を追加——インペイントが効いているかを測る唯一の自動指標約 4 分
4budget.yml — バンドル・モデル（合計 ≤100MB）・出力（.pgs ≤1.0MB）・品質のバジェット判定約 3 分
時間はCIで測れません

GitHubランナーにはGPUがなく Chrome は SwiftShader で動く。実機の20〜50倍遅く、そこで測った生成時間は実機について何も語らない。CIが強制するのはサイズと品質の静的指標のみ。時間は実機で ?bench=1 を使って手動計測し docs/measurements.md に記録する。GitHub Pages は COOP/COEP を返せず SharedArrayBuffer が使えない——WASM がシングルスレッドになることが D5「WebGPU 必須」の根拠。帯域は月100GB。初回 36.6MB なら約2,700訪問で上限。
