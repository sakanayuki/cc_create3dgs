# 実機計測の記録

設計（[07 §7.5](./07-cicd.md#75-性能バジェットの現実的な線引き)）の通り、**時間に関する指標は CI で測れない**。
GitHub ランナーに GPU が無く、そこで測った数字は実機について何も語らないため。
実機での計測はここに記録する。

計測方法: `poc.html` を実機で開いて実行し、結果 JSON をこのファイルに追記する。

---

## 2026-09-07 — PoC-1（Android 10 / Chrome 152）

| | |
|---|---|
| 端末 | Android 10、Chrome 152、画面 412×915 @2.625x |
| WebGPU | **利用不可**（`navigator.gpu` はあるが `requestAdapter` が null） |
| crossOriginIsolated | false（＝WASM 単スレッド） |

Chrome の Android WebGPU は Android 12 以上が要件のため、この端末は対象外。

### 判定

| リスク | 結果 |
|---|---|
| **R1** WebGPU EP が実機で動くか | **この端末では検証不能。** ただし WASM 経路は全モデルで動作 |
| **R10** DA3-Small が動くか | **完全に成功。** 動作し、しかも `intrinsics` と `confidence` まで出力する |
| **R12** 42万サーフェルの fps | **未検証**（WebGPU が無いため） |

### R10 の詳細 — 想定以上の収穫

DA3-Small の ONNX 出力は4つあった。

```
predicted_depth [1,1,518,518]   confidence [1,1,518,518]
extrinsics      [1,1,3,4]       intrinsics [1,1,3,3]
```

`intrinsics` の統計（min 0 / max 702.78 / mean 212.87）を検算すると、
`[fx 0 cx; 0 fy cy; 0 0 1]` で `fx = fy ≈ 702.8`、`cx = cy ≈ 259 = 518/2` として
総和が一致する（実測 1915.9 / 予測 1924.6）。

**焦点距離が直接得られる。** 設計の「EXIF → 画角55°を仮定」というフォールバックが不要になった。
さらに `confidence` は設計に無かった入力で、信頼度の低い画素の深度を捨てる判断に使える。

### WASM 単スレッドでの実測

| モデル | 量子化 | 入力 | 取得 | セッション生成 | 初回推論 | **推論** | DL |
|---|---|---:|---:|---:|---:|---:|---:|
| DA3-S | fp32 | 518² | 9.3 s | 5.2 s | 13.0 s | **13.3 s** | 105.3 MB |
| DA2-S | q4f16 | 518² | 2.3 s | 1.1 s | 19.4 s | **19.8 s** | 19.1 MB |
| DA2-S | fp16 | 518² | 4.3 s | 1.2 s | 18.0 s | **19.6 s** | 49.6 MB |
| DA2-S | uint8 | 518² | 3.2 s | 1.0 s | 16.5 s | **12.9 s** | 27.3 MB |
| MODNet | uint8 | 512² | 2.2 s | 0.4 s | 4.0 s | **4.1 s** | 6.6 MB |
| ISNet | fp16 | 1024² | 6.0 s | 0.4 s | 38.4 s | **37.8 s** | 88.2 MB |
| MI-GAN | fp32 | 512² | 3.5 s | 0.6 s | 5.5 s | **5.6 s** | 28.1 MB |

### ここから分かったこと

**1. WASM では q4f16 が最遅、uint8 が最速。** 設計は全モデルを q4f16 前提にしていたが、
WASM では `MatMulNBits` に速い経路が無く、19.8 s と最悪になった。uint8 の 12.9 s が最速。
**量子化方式はバックエンドで変えなければならない**（→ 決定 D19）。

**2. DA3-S は fp32 のまま DA2-S の fp16 より速い**（13.3 s < 19.6 s）。アーキテクチャが効率的。
量子化すればさらに縮む見込み。

**3. 現行設計を WASM 単スレッドで回すと SLO の 3〜6 倍かかる。**

| 構成 | 所要 |
|---|---:|
| 人物・深度タイルパス無し | 29.6 s |
| 物体・深度タイルパス無し | 63.3 s |
| 深度タイルパス（2×2）を足すと | さらに +52 s |

**4. ISNet の 1024² は WASM では使えない**（37.8 s）。入力解像度を落とすか、
物体モードでも MODNet 系の軽いモデルに寄せる必要がある。

## 2026-09-07 — PoC-2 実機（Android 10 / Chrome 152 / 論理コア 8）

`coi-serviceworker` により **`crossOriginIsolated: true` が実機でも成立した**。
Service Worker による COOP/COEP 付与という手法自体は成功している。

対象: Depth Anything V2 Small (uint8) @518²

| スレッド | セッション生成 | 初回推論 | 推論 | 高速化 |
|---:|---:|---:|---:|---:|
| 1 | 2,266 ms | 11,057 ms | 11,556 ms | 1.00× |
| 2 | 1,660 ms | 6,656 ms | 6,655 ms | **1.74×** |
| 4 | 1,025 ms | 5,714 ms | 6,192 ms | **1.87×** |

### 開発機と実機で傾向がまったく違った

| | 開発コンテナ（4コア均質） | 実機（8論理コア・big.LITTLE） |
|---|---:|---:|
| 2 スレッド | 1.99× | 1.74× |
| 4 スレッド | 3.19〜4.06× | **1.87×** |

論理コアは 8 あるが、スケーリングは **2 スレッドで頭打ち**。大コアが 2 つの
big.LITTLE 構成と見られる。均質なコアを持つ開発機の数字は、携帯機の予測に
使えなかった。**実機で測ったからこそ分かった。**

### サーマルスロットリングの兆候

4 スレッドで **初回推論（5,714 ms）が定常推論（6,192 ms）より速い**。
初回は遅延初期化を含むぶん本来は遅いはずで、この逆転は計測中に発熱で
性能が落ちたことを示唆する。連続生成では 1.87× よりさらに落ちる可能性がある。

### SLO に届くか（人物・軽量プリセット）

PoC-1 の実測（MODNet uint8 4.1 s）と今回の深度 11.6 s を使った見積もり。

| | マット | 深度 | 幾何 | 合計 |
|---|---:|---:|---:|---:|
| 単スレッド | 4.1 s | 11.6 s | 2.0 s | **17.7 s** |
| 2 スレッド | 2.4 s | 6.7 s | 2.0 s | **11.0 s** |
| 4 スレッド | 2.2 s | 6.2 s | 2.0 s | **10.4 s** |

深度を DA3-S uint8（9.5 s と仮定）に置き換えると 15.6 / 9.8 / 9.3 秒。

**結論: マルチスレッド化は必要だが、それだけでは足りない。**
軽量プリセットの 10 秒 SLO にぎりぎり届くかどうかで、余裕がない。

> **注意 — PoC ハーネスの自動判定は誤解を招く表現だった。**
> 「2× 未満なら効果が小さい」という閾値は要件から導いたものではなく、
> 実装時に置いた恣意的な値だった。正しい問いは「SLO に届くか」であり、
> 答えは「マルチスレッド無しでは届かない（17.7 秒）」である。
> 判定ロジックを SLO 基準に修正した。

## 2026-09-07 — PoC-2 参考値（開発コンテナ / 4コア）

実機ではなく開発コンテナ（Chromium 141、論理コア 4）での参考値。
**マルチスレッドの機構が働くこと自体の確認**が目的で、絶対値は実機と異なる。

`coi-serviceworker` により `crossOriginIsolated: true` / `SharedArrayBuffer` 利用可を確認済み。

同梱の合成モデル（畳み込み10層 @512²、0.8 MB）:

| スレッド | 推論 | 高速化 |
|---:|---:|---:|
| 1 | 5,280 ms | 1.00× |
| 2 | 2,654 ms | 1.99× |
| 4 | 1,654 ms | **3.19×** |

2スレッドでほぼ線形（1.99×）、4スレッドで 3.19×。
**マルチスレッド化は WASM 経路にとって最大のレバー**であることが確認できた。

ただしスマートフォンは big.LITTLE 構成で発熱による制限もかかるため、実機ではこれより
低い値になると見込まれる。実機の値は次回の PoC-2 実行で追記する。
